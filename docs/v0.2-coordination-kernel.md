# Chronos v0.2 coordination-kernel profile

Status: source-ready coordination-kernel profile. This is a library/profile
claim, not a complete agent platform or remote wire-service claim. V1 remains
decodable; checkpoint, command, and audit V2 are distinct versioned profiles.

## Boundary and deployment shape

Chronos is the background coordination kernel. It owns bounded task graphs,
eligibility, assignment authority, leases, retries, uncertain-effect fencing,
and durable transition preparation. It remains independent of presentation and
transport.

An agent, human UI, Axon-like chat coordinator, or Vellum-like editing layer
should reach Chronos through a separately versioned orchestration/service
adapter. That adapter owns authentication, authorization policy, networking,
sessions, subscriptions, process supervision, clocks, and translation between
external schemas and Chronos values. It must not become an alternate task-state
writer.

The intended flow is:

1. the adapter authenticates a principal and derives a bounded capability
   assertion;
2. Chronos issues opaque, expiring, selectively revocable claim authority;
3. the caller reads authority-free revisioned projections and requests either
   deterministic selection or an exact targeted claim;
4. a connector executes under one lease and reports completion, failure, or
   immediate uncertainty;
5. each authoritative command is sealed with its canonical checkpoint and only
   released after the configured persistence acknowledgement;
6. chat and editor events carry references and correlations, never lease tokens
   or mutable scheduler state.

Chat is coordination evidence, not scheduler truth. Vellum owns editable
project/task documents and may propose graph changes; Chronos admits only a
closed, validated task projection. Axon or its successor may orchestrate
conversation and tool execution, but scheduling policy and lease transitions
remain in Chronos.

## Delivered kernel slices

- Atomic finite graph admission validates shape, capacity, references, and
  acyclicity before publishing any member.
- Targeted claim assigns exactly one named ready and compatible task without
  running unrelated expiry/dependency housekeeping on refusal.
- A live lease holder can immediately fence an effect as unknown; the old lease
  is revoked and reconciliation is mandatory.
- `TaskSnapshotV1` is a bounded content-minimized read model with no identity,
  content, principal, failure text, idempotency material, attempt identity, or
  lease authority.
- Grants can be revoked individually. Optional finite claim budgets are consumed
  only by published claims; refusal and empty selection do not consume budget.
  Engine-owned grant state has an explicit capacity and monotone-time expiry
  sweep, so discarded expired tokens cannot retain capacity indefinitely.
- `PreparedTransitionV1` consumes the engine, seals its command outcome and
  candidate engine, exposes only checkpoint material, and releases ownership
  only after receipt attribution and acknowledgement strength are validated.
  Discard, bad receipt, and checkpoint-encoding failure drop candidate authority.
- Engine-issued task incarnations never reuse the identity of a retired task.
  Retirement requires an exact terminal reference and zero active dependents;
  checkpoint V2 persists the high-water mark even with no active tasks.
- Task-state revisions form a bounded total-order lattice with explicit top.
  Exact snapshots and bounded lexical pages carry revisions; stale cursors and
  V2 task mutations refuse before authority or budget is consumed, including at
  explicit top, where no indistinguishable task successor can be published.
- Engine-issued time observations establish a non-regressing persisted floor.
  Only the current observation is accepted by V2 temporal operations, and
  recovery invalidates old observations in a fresh authority namespace.
- `CommandV2` is a closed coordination vocabulary using revision/incarnation
  and monotone-time guards. `AuditRecordV2` has separate stable tags and a
  bounded pre-mutation-backpressure journal.
- `TaskSpecV2` stores no work summary or raw idempotency key. V2 failure commands
  retain only a closed scheduler failure class; detailed content stays in
  authorized Vellum/chat/connector storage.
- Checkpoint V2 canonically persists incarnation, task-state revision, and time
  floor/sequence. Immutable V1 and V2 fixtures are both decoded and robustness
  tested.

These additions are library APIs and in-process command profiles. They do not
reinterpret closed V1 formats and are not a stable remote wire protocol.

## External and later-profile obligations

- A remote transport schema, authentication/authorization adapter, subscription
  protocol, and bounded change-feed retention/cursor-expiry policy.
- A transactional deployment strategy if checkpoint publication and durable
  audit append must be atomic across different physical systems. The included
  journal is a bounded outbox contract, not that distributed transaction.
- Connector conformance for effect attribution, idempotency scope, cancellation,
  lease loss, reconciliation, and redaction.
- Backpressure and quotas for subscribers, principals, projects, workers, graph
  batches, and change retention. Slow consumers cannot retain unbounded history.
- TLC, coverage-guided fuzzing, broad mutation scoring, advisory scanning, and
  dependency-policy tools remain named gates but were unavailable on the
  executed host; their absence is not a pass.

Later scheduling profiles may add pause, supersession, not-before eligibility,
deadlines, aging/fair-share, affinity, and resource/cost placement. Each requires
a named closed policy and laws; none silently alter `StrictPriorityV1`.

## Algebraic operating constraints

The service boundary must preserve the engine's categorical closure:

- commands are a finite versioned coproduct interpreted as total state
  transitions;
- refusal is the identity transition for authoritative state;
- batches are bounded free words unless explicitly given all-or-nothing graph
  semantics;
- observations are coalgebraic projections and never mutation capabilities;
- evidence aggregation uses a bounded lattice only where joins and meets are
  honest;
- retained histories are funded, bounded cofree observations with explicit
  truncation/cursor semantics;
- resource accounting is a checked ordered commutative monoid with an explicit
  overflow/capacity element;
- external effects remain outside the kernel until represented by a typed,
  bounded evidence contract.

## Security and privacy deltas

STRIDE additions:

- selective grant identity prevents one compromised worker token from requiring
  fleet-wide revocation; global epoch revocation remains the emergency join;
- exact claim prevents a human selection from being confused with scheduler
  choice;
- prepared transitions prevent uncommitted leases or grants escaping after a
  persistence failure;
- graph admission rejects prefix publication and dependency-confusion attacks;
- explicit uncertainty fencing prevents timeout-driven duplicate effects.

LINDDUN additions:

- snapshots omit task and principal content, but lookup timing and aggregate
  counts can still disclose workload shape and require adapter authorization;
- grant budgets and revocation status must remain absent from metric labels and
  debug surfaces;
- checkpoint bytes, command inputs, chat correlations, Vellum document links,
  and targeted task IDs remain sensitive at the adapter boundary;
- remote change feeds require bounded retention, audience filtering, cursor
  expiry, and deletion/retirement semantics.

## Release evidence gates

The source-ready claim is backed by green unit/BDD suites, algebraic laws,
independent reference models, bounded exhaustive exploration, immutable V1/V2
fixtures, deterministic corruption corpora, fault-injected durability tests,
instrumentation privacy checks, an explicit host performance budget,
STRIDE/LINDDUN review, and requirement traceability. Unavailable external tools
and external connector/service evidence remain unclaimed.
